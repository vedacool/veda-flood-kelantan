# How VEDA works
_Module contracts (inputs → outputs → failure behaviour). Filled in as modules are built._

## Guard rails (B-65) — `scripts/codemap.py`, `scripts/precommit.py`, `tests/test_architecture.py`, `.githooks/`
- **Inputs:** the repo's Python files (`app/`, `scripts/`, `run.py`), all git-tracked files (secret scan), the local `.env` (only to know which secret values must never appear), the commit message.
- **Outputs:** `docs/CODEMAP.md` (module → purpose, public functions, callers), regenerated and staged on every commit; pass/fail for 6 guard rules; pass/fail for the backlog-ID check.
- **Failure behaviour:** any failed rule exits non-zero → git refuses the commit and prints the file:line and the rule broken. Secret values are never printed, only where they were found. Rules 1–2 skip `spikes/`; the secret scan covers every tracked file.

## Trace logger (B-02) — `app/trace.py`
- **Inputs:** `start_run(question)` once per run; then `step(agent, action, input_summary, output_summary, status, target_agent, confidence, retry_count, source, decision, duration_ms, details)` for every agent step, Zetaris call and Nightshift call; `end_run(status)`.
- **Outputs:** `logs/trace-<run_id>.jsonl`, one JSON line per step (official FAQ fields + `run_id`, `step`, `decision`, `source`, `mode`, `duration_ms`, `details`), with `run_start` / `run_end` lines; one readable sentence per step on stdout. `python -m app.trace <file>` replays a trace as sentences.
- **Failure behaviour:** unknown `status` → `ValueError`; `step()` before `start_run()` → `RuntimeError` (no silent lost steps). A failed disk write prints a warning and the run continues. Summaries are capped at 300 characters, and secrets (Bearer/nvapi/password patterns + any secret value in the environment) are replaced by `***` before writing.
- **Statuses:** `success`, `failed`, `retrying`, `fallback`, `needs_revision`, `approved`, `injected_fault`.

## Nightshift adapter (B-03) — `app/adapters/nightshift.py`
- **Inputs:** `chat(lane, messages, agent, json_mode=False, thinking=False, tools=None, max_tokens=2000)` with lane `fast` or `deep`. Env: `METERLESS_BASE_URL`, `METERLESS_RUNTIME_TOKEN`, `METERLESS_MODEL_FAST/DEEP` (default `fast`/`deep`), `METERLESS_APP_FAST/DEEP` (default `veda-fast`/`veda-deep` — the `meterless-app` header; Nightshift pins routing mode per app). `get_llm(lane, agent)` gives the Meterless engine-style generator `generator(prompt, attachments, system_prompt, on_stream, abort_signal) -> {"text"}`.
- **Outputs:** `LLMResult` (text, parsed `data` in JSON mode, tool_calls, served_model, routed_mode, mode_coerced, pinned, attempts, latency, usage). One trace line per call with the model that actually answered. `pinned` is true only if Nightshift honoured the lane AND the expected model answered (`METERLESS_EXPECT_FAST/DEEP`, default Nemotron 3.5 Lightning / Super VL); otherwise the line says "Lane NOT pinned …" or "WRONG MODEL on lane …".
- **Failure behaviour:** unknown lane or any `auto` model → `ValueError`. 429/5xx/network → retry after 2/4/8 s (each retry traced), then `NightshiftError`. `empty_response` → one retry with double `max_tokens`. 401 → no retry, `NightshiftError` naming the env var. Invalid JSON → one repair request, then `NightshiftError`. `max_tokens` never below 200. In SAMPLE_MODE it refuses live calls (`NightshiftError`) until the SampleGenerator (B-18). The caller decides the fallback. The token is never logged.

## Zetaris adapter (B-04) — `app/adapters/zetaris.py`
- **Inputs:** `run_sql(sql, agent, purpose=None, limit=1000)` — one `SELECT`/`WITH` statement. `run_ddl(sql, agent, purpose=None)` — one allow-listed DDL statement (`CREATE LIGHTNING REST TABLE`, `CREATE [OR REPLACE] SCHEMASTORE VIEW`, `CACHE TABLE`, `DROP LIGHTNING DATABASE TABLE`, `REGISTER DATASOURCE TABLES`). Env: `ZETARIS_API_URL`, `ZETARIS_API_KEY`, `ZETARIS_ORG_ID`, `ZETARIS_RECORD`, `SAMPLE_MODE`.
- **Outputs:** `SqlResult` — `columns`, typed `rows`, `records` (rows as dicts), `row_count`, `query_hash`, `source` (`zetaris-live` / `zetaris-replay`), `fetched_at`, `duration_ms`. Numbers become int/float; text with a leading zero (station IDs) and dates stay text. One trace line per call. With `ZETARIS_RECORD=true` each result is saved to `data/fixtures/zetaris/<query_hash>.json` (hash of the whitespace-normalised SQL). In `SAMPLE_MODE` the fixture is replayed and the network is never touched.
- **Failure behaviour:** raises `ZetarisError` with `kind`: `not_allowed` (not SELECT/WITH, several statements, DDL off the allow-list) · `auth` (401, no retry) · `sql` (Zetaris rejects the query, no retry) · `source_unavailable` (the REST source behind a table failed, e.g. data.gov.my 429 — caller uses cache/backup) · `network` (after retries at 2 s and 4 s) · `no_fixture` (SAMPLE_MODE without a recording). DDL "already exists" counts as success (`run_ddl` returns False). DDL never runs in SAMPLE_MODE. The API key is never logged.

## Postgres store (B-05) — `db/schema.sql`, `scripts/setup_pg.py`
- **Inputs:** `.env` (`VEDA_PG_PASSWORD` superuser, `VEDA_PG_RO_PASSWORD` read-only role, `ZETARIS_*`); Docker with Zetaris running.
- **Outputs:** container `veda-pg` (postgres:16-alpine, host port 5433, volume `veda-pg-data`) on network `zetaris_default`; tables `stations`, `river_levels`, `places`, `historic_peaks`, `source_registry`; role `veda_zetaris` with SELECT only; Zetaris datasource `veda_pg` (`jdbc:postgresql://veda-pg:5432/veda`) with its tables registered. Python writes to Postgres directly; agents read only through `run_sql("... FROM veda_pg.<table>")`.
- **Failure behaviour:** every step is traced; any failure stops the script with `SETUP FAILED: …` and a failed `run_end`. Re-running is safe: `IF NOT EXISTS` tables, "already exists" datasource treated as success, `REGISTER DATASOURCE TABLES` re-run each time to pick up new tables. Refuses to run in SAMPLE_MODE. Passwords never appear in traces.

## JPS collector (B-06) — `app/ingest/jps.py`, `app/adapters/pg.py`
- **Inputs:** the JPS Public Infobanjir Kelantan page (`…/aras-air-data/?state=KEL&district=ALL&station=ALL&lang=en`), or a saved snapshot (`--from-file`). Env: `VEDA_PG_PASSWORD`.
- **Outputs:** `stations` upserted (name, district, river, visible JPS id, 4 thresholds — the data.gov.my mapping and lat/lon are left for B-67) and new rows in `river_levels` (UTC `observed_at`, `level_m`, `source` = `jps-live` / `jps-cache` / `jps-snapshot`). `station_key` = the JPS graph-link id (e.g. `_DKBR0007`), never blank, equal to the data.gov.my id for 24/36 stations. Raw HTML of every live fetch is kept in `data/cache/jps/`. Agents read the result only through Zetaris (`veda_pg.river_levels`, `veda_pg.stations`).
- **Failure behaviour:** at most one live fetch per 15 minutes (a newer cached snapshot is reused, no override). Missing columns, no rows, rows without a graph link or duplicate ids → `JpsParseError`, nothing stored, previous data kept. Network/HTTP errors are traced and nothing is stored; the next cycle retries. Values `-`, blank, `-9999` → NULL, never 0. Re-ingesting the same page adds 0 rows (primary key station + time). `--loop` keeps going after a failed cycle.

## Nightshift configuration VEDA needs (B-66) — outside the repo
Nightshift pins nothing by itself: the app `mode` (`fast`/`deep`) is a core mode ("prefer speed / quality"), not a lane. Each VEDA app needs a **lane allowlist** in `%LOCALAPPDATA%i.meterless.runtime\statepp-policy.json` (edit only while Nightshift is closed):
`"veda-fast": {"mode": "fast", "lanes": ["fast"]}`, `"veda-deep": {"mode": "deep", "lanes": ["deep"]}`.
Lanes in `lanes.toml`: `fast` = Nemotron 3.5 Lightning, `deep` = Nemotron 3.5 Super VL, both `role = "race"`, `races = true` (a `verify` role or `races = false` lane never answers). Check: every trace line says "Answered by … on lane …"; "WRONG MODEL" or "Lane NOT pinned" means this config was lost.
