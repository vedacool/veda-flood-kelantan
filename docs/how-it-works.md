# How VEDA works
_Module contracts (inputs → outputs → failure behaviour). Updated with every module change; last full pass after the 2026-10-22 audit fixes._

## Shared settings — `app/config.py`
- **What:** one place for the `SAMPLE_MODE` / other env flags (`flag()`, `sample_mode()`), Malaysia time (`MYT`), the Postgres address (`127.0.0.1:5433`, db `veda`) and the secret patterns used by both the trace redactor and the commit-time secret scan.
- **Secret rules:** values of VEDA's own env keys (`METERLESS_*`, `ZETARIS_*`, `VEDA_*`, `NVIDIA_*`, `PG*` containing TOKEN/KEY/PASSWORD/SECRET) plus patterns for NVIDIA keys, Bearer/Basic auth, URL credentials, private keys, quoted passwords/tokens/API keys and `KEY=value` assignments. Placeholders (`{PW}`, `<token>`, `$VAR`, `***`) and code (`os.environ["X"]`) are not treated as secrets.

## Guard rails (B-65) — `tests/test_architecture.py`, `scripts/codemap.py`, `scripts/precommit.py`, `.githooks/`, `.github/workflows/ci.yml`
- **Inputs:** the repo's Python files (`app/`, `scripts/`, `run.py`), the **staged** content (and working-tree copy) of every tracked file, the local `.env` (only to know which secret values must never appear), the commit message.
- **Outputs:** `docs/CODEMAP.md` regenerated and staged on every commit; pass/fail for **8 rules**: (1) agents never touch network/DB/shell/dynamic imports directly (`requests`, `psycopg`, `subprocess`, `importlib`, `app.adapters.pg`, `app.ingest`, `__import__`/`exec`/`eval`…), (1b) agents never pass `setup=` to `run_ddl`, (2) no `meterless/auto`, (3) nothing reads `output_examples/` at runtime, (4) every agent imports the trace logger, (5) no secrets in staged files, (6) `.env` never tracked, (7) no invisible control characters; plus the backlog-ID check on the commit message. CI runs the same tests, `codemap --check`, `pip-audit` on `requirements-lock.txt` and gitleaks over the full git history on every push.
- **Failure behaviour:** any failed rule exits non-zero → git refuses the commit (and CI goes red) and prints file:line and the rule broken. Secret values are never printed, only where they were found. Rules 1–2 skip `spikes/`; rules 5–7 cover every tracked file.

## Trace logger (B-02) — `app/trace.py`
- **Inputs:** `start_run(question)` once per run; then `step(agent, action, input_summary, output_summary, status, target_agent, confidence, retry_count, source, decision, duration_ms, details)` for every agent step, Zetaris call and Nightshift call; `end_run(status)`. `trace.bind(fn)` carries the current run into a plain worker thread/executor; each call runs in its own context copy, so one bound function can run in many threads at once (B-17 parallel queries). FastAPI's threadpool does this by itself.
- **Outputs:** `logs/trace-<run_id>.jsonl` (run id in MYT), one JSON line per step (official FAQ fields + `run_id`, `step`, `decision`, `source`, `mode`, `duration_ms`, `details`), with `run_start` / `run_end` lines; one readable sentence per step on stdout, timed in MYT on any machine. `python -m app.trace <file>` replays a trace as sentences.
- **Failure behaviour:** unknown `status` in `step()` → `ValueError`; `step()` before `start_run()` → `RuntimeError` (no silent lost steps); `end_run()` always closes the run (a bad status becomes `failed`). A failed disk write prints a warning and the run continues. Summaries are capped at 300 characters and redacted with the shared secret rules before writing; Malaysian phone numbers and MyKad (IC) numbers are replaced by `[phone]` / `[IC]` (B-56 — no personal data in traces), while gauge ids, run ids, timestamps and coordinates are left intact.
- **Statuses:** `success`, `failed`, `retrying`, `fallback`, `needs_revision`, `approved`, `injected_fault`.
- **Live listener (B-17):** `start_run(question, listener=fn)` calls `fn(record)` after every step is written; a failing listener prints a warning and never stops the run.

## Nightshift adapter (B-03) — `app/adapters/nightshift.py`
- **Inputs:** `chat(lane, messages, agent, json_mode=False, thinking=False, tools=None, max_tokens=2000, temperature=0.2, target_agent=None, budget_s=None)` with lane `fast` or `deep`. Env: `METERLESS_BASE_URL`, `METERLESS_RUNTIME_TOKEN`, `METERLESS_MODEL_FAST/DEEP` (default `meterless/fast`/`meterless/deep`), `METERLESS_APP_FAST/DEEP` (default `veda-fast`/`veda-deep` — the `meterless-app` header; Nightshift pins routing per app), `METERLESS_EXPECT_FAST/DEEP` (default Nemotron 3.5 Lightning / Super VL). `get_llm(lane, agent)` gives the Meterless engine-style generator `generator(prompt, attachments, system_prompt, on_stream, abort_signal) -> {"text"}`.
- **Outputs:** `LLMResult` (text, parsed `data` in JSON mode, tool_calls, served_model, expected_model, routed_mode, mode_coerced, pinned, attempts, latency, usage). One trace line per call with the model that actually answered. `pinned` is true only if Nightshift honoured the lane AND the expected model answered; otherwise the line says "Lane NOT pinned …" or "WRONG MODEL on lane …".
- **Failure behaviour:** unknown lane or any `auto` model → `ValueError`. 429/5xx/network, and bodies that are not a proper JSON object (string/list errors, 200 without choices) → retry after 2/4/8 s (each retry traced), then `NightshiftError`. `budget_s` caps the whole call incl. retries and the JSON repair (pass the run's remaining time). `empty_response` → one retry with double `max_tokens`. 401 → no retry. Invalid JSON → one repair request, then `NightshiftError`. `max_tokens` never below 200. In SAMPLE_MODE it refuses live calls until the SampleGenerator (B-18). The caller decides the fallback. The token is never logged; CLI errors are redacted. **22 Oct night:** per-lane timeout (fast 60 s, deep 100 s); **Streaming** (`STREAM = True`): the answer is read as an event stream and assembled (content, served model, Nightshift receipt, usage), with a hard total limit per call; a stream `error` event (e.g. `ttfb_timeout`, `provider_deadline`) is a failure with Nightshift's reason; a plain JSON reply still works. `max_attempts=1` = one try, no retry and no JSON repair round (the agents use it: Nightshift cuts calls at ~45 s with HTTP 502 `ttfb_timeout`, so a retry mostly burns another 45 s).

## Zetaris adapter (B-04) — `app/adapters/zetaris.py`
- **Inputs:** `run_sql(sql, agent, purpose=None, limit=1000, budget_s=None)` — one read-only statement. `run_ddl(sql, agent, purpose=None, setup=False, budget_s=None)` — one allow-listed DDL statement. Env: `ZETARIS_API_URL`, `ZETARIS_API_KEY`, `ZETARIS_ORG_ID`, `ZETARIS_RECORD`, `SAMPLE_MODE`.
- **SQL handling:** a small scanner understands quotes (incl. doubled and backslash escapes) and comments. `--` and `/* */` comments are removed (they can never swallow a following clause), whitespace is collapsed only outside quotes (literals keep their exact text), one statement only.
- **Read-only rule:** must start with `SELECT`/`WITH` AND contain none of `INSERT UPDATE DELETE MERGE DROP CREATE ALTER CACHE UNCACHE REFRESH TRUNCATE SET ADD LOAD GRANT REVOKE REGISTER INTO MSCK ANALYZE EXEC EXECUTE CALL` or `reflect(` / `java_method(` outside quotes.
- **DDL rule:** agents (`setup=False`) may only `CACHE TABLE` or `CREATE LIGHTNING REST TABLE` whose endpoints are `https` on `api.data.gov.my`, `api.open-meteo.com` or `flood-api.open-meteo.com`. Setup scripts (`setup=True`) may also create/replace/drop SchemaStore views, drop lightning tables, create lightning databases and containers, register/create datasources.
- **Outputs:** `SqlResult` — `columns`, typed `rows`, `records`, `row_count`, `query_hash`, `source` (`zetaris-live` / `zetaris-replay`), `fetched_at`, `duration_ms`. Numbers become int/float (non-finite values like `1e400` stay text); text with a leading zero (station IDs) and dates stay text. With `ZETARIS_RECORD=true` each result is saved to `data/fixtures/zetaris/<query_hash>.json`; in `SAMPLE_MODE` the fixture is replayed and the network is never touched.
- **Failure behaviour:** `ZetarisError` with `kind`: `not_allowed` (write/DDL in run_sql, several statements, DDL off the allow-list, unterminated quote/comment) · `auth` (401) · `sql` (Zetaris rejects the query) · `source_unavailable` (the REST source behind a table failed, e.g. data.gov.my 429 — caller uses cache/backup) · `network` (after retries at 2 s and 4 s, incl. 200 responses whose body is not a JSON object) · `bad_response` (rows don't match the column list) · `no_fixture`. `budget_s` caps total retry time. DDL "already exists" counts as success. DDL never runs in SAMPLE_MODE. The API key is never logged.

## Postgres store (B-05) — `db/schema.sql`, `scripts/setup_pg.py`, `app/adapters/pg.py`
- **Inputs:** `.env` (`VEDA_PG_PASSWORD` superuser, `VEDA_PG_RO_PASSWORD` read-only role, `VEDA_PG_WRITER_PASSWORD` writer role — role passwords must be 16+ of `A-Z a-z 0-9 _ -`; `ZETARIS_*`); Docker with Zetaris running.
- **Outputs:** container `veda-pg` (postgres:16-alpine, **published on 127.0.0.1:5433 only**, volume `veda-pg-data`) on network `zetaris_default`; tables `stations`, `river_levels`, `places`, `historic_peaks`, `source_registry`; constraints `river_levels_station_fk`, `places_station_fk`, `river_levels_level_range` (−50…1000 m), `river_levels_not_future`, `stations_threshold_range`; roles `veda_zetaris` (SELECT only — Zetaris reads) and `veda_writer` (SELECT/INSERT/UPDATE on `stations`, `river_levels` — the JPS collector writes); Zetaris datasource `veda_pg` with its tables registered. `pg.transaction()` gives ingest jobs one transaction as `veda_writer` (statement timeout 30 s).
- **Failure behaviour:** every setup step is traced; any failure stops with `SETUP FAILED: …` (redacted) and a failed `run_end`. Docker calls time out after 60 s. Re-running is safe: `IF NOT EXISTS` tables, constraints added only when missing, "already exists" datasource treated as success, `REGISTER DATASOURCE TABLES` re-run each time. A container published on all interfaces is re-created bound to 127.0.0.1 (data stays in the volume). `pg` raises `PgError` for missing config, unreachable server or any database error. Refuses to run in SAMPLE_MODE. Passwords never appear in traces.

## JPS collector (B-06) — `app/ingest/jps.py`
- **Inputs:** the JPS Public Infobanjir Kelantan page, or a saved snapshot (`--from-file`, the only mode allowed in SAMPLE_MODE). Env: `VEDA_PG_WRITER_PASSWORD` (checked before any fetch).
- **Outputs:** `stations` upserted (name, district, river, visible JPS id, 4 thresholds — **a missing value never overwrites a stored one**; data.gov.my mapping and lat/lon are left for B-67) and readings in `river_levels` (UTC `observed_at`, `level_m`, `source` = `jps-live` / `jps-cache` / `jps-snapshot`). Rows without a level are not stored; a changed value for the same station + time is corrected. `station_key` = the JPS graph-link id (validated `[A-Za-z0-9_]{1,40}`; malformed rows are skipped and counted). Raw HTML of every live fetch is kept in `data/cache/jps/` (names in MYT). Agents read the result only through Zetaris.
- **Numbers:** `-`, blank, `N/A`, `nan`, `inf`, `±9999` sentinels, values outside −50…1000 m and ambiguous decimal commas (`7,47`) → NULL, never 0 and never a guess. Unicode minus is accepted.
- **Failure behaviour:** at most one live fetch per 15 minutes (a snapshot dated in the future is not trusted). Page > 2 MB, missing columns, no valid rows or duplicate ids → `JpsParseError`, nothing stored. Network/HTTP errors are traced and nothing is stored. Database errors → `PgError`, the transaction rolls back. `--loop` survives **any** failed cycle and tries again 15 minutes later; only a configuration error (e.g. live fetch in SAMPLE_MODE) stops it; Ctrl+C closes the trace cleanly.

## Nightshift configuration VEDA needs (B-66) — outside the repo
Nightshift pins nothing by itself: the app `mode` (`fast`/`deep`) is a core mode ("prefer speed / quality"), not a lane. Each VEDA app needs a **lane allowlist** in `%LOCALAPPDATA%\ai.meterless.runtime\state\app-policy.json` (edit only while Nightshift is closed):
`"veda-fast": {"mode": "fast", "lanes": ["fast"]}`, `"veda-deep": {"mode": "deep", "lanes": ["deep"]}`.
Lanes in `lanes.toml`: `fast` = Nemotron 3.5 Lightning, `deep` = Nemotron 3.5 Super VL, both `role = "race"`, `races = true` (a `verify` role or `races = false` lane never answers). Check: every trace line says "Answered by … on lane …"; "WRONG MODEL" or "Lane NOT pinned" means this config was lost. The Cockpit warning "No lane has duty Judge or Verify" is **expected and harmless** for VEDA: it concerns Nightshift's overnight panel-judging jobs, which VEDA does not use (our Critic agent is the judge). **Never click its fix** ("Set Verify on fast"): a Verify lane stops answering and would break `veda-fast`.

## Station mapping (B-67) — `data/stations_mapping.csv`, `scripts/seed_stations.py`
- **Inputs:** `data/stations_mapping.csv` — the single, human-reviewed source of truth: one `gauge` row per curated gauge (16: the 5 core stations from BUILD_BRIEF plus upstream sentinels on the Galas, Lebir and Golok arms and the controlling gauges for Pasir Mas, Kota Bharu and Tumpat) and one `link` row per relation (`upstream_of` along a chain, `backup_for`, `travel_time` with a lag range). Every row carries its source and a status (`verified - …` or `tentative - needs Dr Ariff`). Review columns (JPS thresholds today, the 2014 JPS table, map links) are for people; the seed reads only the curated fields.
- **Outputs:** curated columns on `stations` (`brief_name`, `is_core`, `chain`, `chain_order`, `role`, `controls_town`, `backup_of`, `mapping_status`, `mapping_note`, `coords_source`, lat/lon) and the `station_links` table (`lag_min_h`, `lag_max_h`, `lag_source`, `status`), all readable through Zetaris (`veda_pg.stations`, `veda_pg.station_links`).
- **Failure behaviour:** `validate_mapping()` refuses the whole file on any problem (unknown key, duplicate, bad coordinates outside Kelantan, bad link type, self-link, lag min > max or negative, upstream loop, …) and writes nothing. Seeding is one transaction that first clears every curated column and link, then writes the CSV — re-running is safe and a row removed from the CSV disappears. The JPS collector never touches the curated columns. `--check-only` validates without writing.

## Weather and warning sources (B-07) — `scripts/setup_wx.py`, `data/rain_points.csv`
- **Inputs:** `data/rain_points.csv` — reviewed list of rain points (5 core gauges + Galas and Lebir upstream catchments; coordinates from data.gov.my; all "tentative - needs Dr Ariff"; Thai-side Golok points deferred as a known gap). Fixed public URLs for data.gov.my.
- **Outputs:** Lightning database `VEDA_WX` with four cached REST tables, all read through `run_sql`: `om_rain` (Open-Meteo, **one table for all points** — one row per point, `location_id` = CSV order; hourly rain + probability, daily totals, past 7 + next 7 days, Malaysia time), `mygov_forecast` (district forecast), `mygov_warning` (MetMalaysia warnings), `mygov_flood` (data.gov.my `/flood-warning` for Kelantan — **frozen since 23 Feb 2024**, kept so the Critic can catch a stale source).
- **Gotchas:** Open-Meteo leaves `location_id` empty for the first point → always read `COALESCE(location_id, 0)`. It snaps each point to its weather grid (returned lat/lon differ slightly from the request). A REST table's URL is fixed when created → after editing the CSV run `setup_wx.py --recreate`.
- **Failure behaviour:** the points file is validated first (order, unique keys, coordinates in/next to Kelantan, sources filled) and nothing is created if it fails. Creation is idempotent ("already exists" = success); `--refresh` re-fetches every source now (uncache + cache); every step and the smoke check are traced; errors stop with `SETUP FAILED` (redacted). Tables are cached so data.gov.my's ~4 requests/minute limit is never hit by queries.

## Historic peaks (B-55) — `data/historic_peaks.csv`, `scripts/seed_peaks.py`
- **Inputs:** `data/historic_peaks.csv` — every row cites its own https source. `official`: the JPS "Laporan Catatan Aras Air Tertinggi" 01-12-2014 to 10-02-2015 table (8 gauges, with the thresholds in force then), from USM CGSS slides. `news`: verified newspaper figures for Dec 2023 and Nov 2024 (NST, Kosmo, Malay Mail), kept separate; where sources disagree both rows stay (Rantau Panjang 2014: JPS 10.84 m vs Kosmo 10.52 m; Tambatan Diraja 29 Nov 2024: 5.47 vs 5.53 m). Unverifiable figures are left out (10.97 m).
- **Outputs:** `historic_peaks` rows (peak, when, source type/name/URL, thresholds then, notes), readable through Zetaris. `compare_lines()` gives one plain sentence per core station — latest reading **with its reading time in MYT** vs the official Dec 2014 peak.
- **Failure behaviour:** `validate_peaks()` refuses the file on any problem (unknown station, missing/duplicate event, non-https source, missing source name, bad or out-of-range numbers) and writes nothing. Seeding replaces all peaks in one transaction; re-running is safe. Whether a reading is too old to use is not decided here (freshness limits are KIV) — the line always shows the reading time so nothing stale is called "now".

## Zetaris views (B-08) — `db/views/*.sql`, `scripts/setup_views.py`
- **Inputs:** veda-pg tables (`stations`, `river_levels`, `rain_points`) and the VEDA_WX REST tables (`om_rain`, `mygov_forecast`), all through Zetaris.
- **Outputs:** SchemaStore container `veda`, read with `run_sql("SELECT … FROM veda.<view>")`:
  `river_status_latest` (one row per gauge: latest level, `observed_at_utc`, `age_minutes`, thresholds, `band` = below_normal / normal / alert / warning / danger / no_reading, `change_1h_m`, `change_3h_m`, curated mapping) ·
  `rain_24h_by_point` (one row per rain point: rain past 24 h / 7 d, next 24 h / 72 h, max probability next 24 h) ·
  `forecast_kelantan` (one row per Kelantan state / district / town per day, incl. the Rantau Panjang town forecast) ·
  `station_risk_inputs` (one row per core station: the three fused). `place_risk_inputs` (one row per place) is added with the gazetteer in B-09.
- **Rules:** views hold **facts** (age, band, change, rain sums); **judgements** (fresh / aging / stale, verdicts) are made in Python with the tentative defaults in one place. Zetaris runs in GMT: river times are UTC, Open-Meteo times are MYT, and the rain view converts "now" to MYT explicitly (cross-checked against an independent Python sum). A change value is empty — never 0 — when no reading exists 1 h / 3 h earlier (e.g. a stale gauge).
- **Failure behaviour:** each view file must be one read-only SELECT (same rule as `run_sql`) or the script refuses it; views are `CREATE OR REPLACE` (setup-only DDL — agents cannot replace a view). Known gap: the views cannot tell when the cached Open-Meteo forecast was fetched, so its freshness is checked by the Data & Reconciler agent (B-13) from recorded refresh times.

## Place gazetteer (B-09) — `app/gazetteer.py`, `data/places.csv`, `scripts/seed_places.py`
- **Inputs:** what the user typed. Covered places come from `data/places.csv` (reviewed; first four: Pasir Mas town, Rantau Panjang, Kota Bharu, Tumpat — coordinates from Open-Meteo geocoding / GeoNames, town forecast ids, aliases and spelling variants, controlling / secondary / sentinel gauges per the review pack C6, all "tentative - needs Dr Ariff").
- **Outputs:** `resolve(text)` → `Resolution(status, place, suggestions, message, known, nearest, covered)`: `found` (exact alias, or an alias inside a longer sentence — longest wins), `did_you_mean` (close spelling via difflib ≥ 0.75; **never picks a place by itself**), `not_covered` ("X is in Kelantan but not covered yet" for known Kelantan names from the MetMalaysia list, otherwise generic; always lists the covered places). One trace line per call. Reads only through `run_sql` → works offline in SAMPLE_MODE from the committed fixtures in `data/fixtures/zetaris/`. Views: `veda.place_risk_inputs` (one fused row per place: controlling gauge + nearest rain point + today's town forecast) and `veda.place_gauge_status` (one row per place × gauge, with the reported travel time to the controlling gauge when known, e.g. Kuala Krai → Tambatan Diraja 9–17 h for Kota Bharu).
- **Nearest covered place (B-21):** for a known but uncovered Kelantan district, `nearest_covered()` takes the average position of that district's stations in data.gov.my `/flood-warning` (its levels are frozen, station positions are not) and returns the closest covered place with the distance rounded to 5 km; no position → no suggestion. `card.place_reply(res, lang)` words the reply in BM or EN ("Kelantan" alone → "please name a town or district").
- **Failure behaviour:** unknown names never raise — they return `not_covered`. `validate_places()` refuses the file on any problem (kind, coordinates outside Kelantan, missing controlling gauge, unknown or repeated gauge, empty forecast id, alias that normalises to nothing or belongs to two places). Seeding replaces the gazetteer in one transaction; each place's nearest rain point is computed by straight-line distance. Kampung and school names are not covered yet (clear reply, no guessing).

## World Model engine (B-10, Meterless) — `app/engines/world_model/`
- **What it is:** VEDA's shared, provenance-stamped world state, a Python implementation of the Meterless World Model engine (spec: `Sponsor - Meterless - World Model Engine`; reference: github.com/Meterless/Meterless `engines/world-model`, Apache-2.0). Hybrid shape: a bitemporal **graph** (stations, places, rivers, districts, sources + typed edges with `valid_from` / `valid_to`) plus timestamped **facts** (water level at T, rain, forecast; later stale / conflict facts from the Critic).
- **Inputs:** `upsert_entity(type, name | external_key, attrs, source)`, `upsert_context(...)`, `relate(from, type, to, valid_from, context, source)`, `assert_fact(about, predicate, value, confidence, source)`, `ingest(observations)`. Every `source` must carry `kind` + `at` (plus, for VEDA, `query_hash`, `agent`, `run_id`).
- **Outputs:** state rebuilt from an **append-only event log** (memory, or SQLite at `data/world/…`, gitignored) — `neighbors_of(id, via, at)`, `edges(...)`, `facts_about(...)`, `entity(...)`, `audit()` (strictly increasing seq, optionally mirrored to `logs/worldmodel-audit-<run>.jsonl`), `state_shape_canonical()` (equal strings = equal worlds), `manifest()` (which spec services are live vs dormant).
- **Rules (each is an official conformance check):** stable ids — NFKD, accents / NBSP / zero-width stripped, `ent_` + sha256[:16], `type:system:id` for external keys (sid-001/002) · near-duplicate names: ≥ 0.85 auto-merge, 0.82–0.85 review queue, else new (band-001) · no provenance, no write (prov-001) · ingest is idempotent, an edited observation changes the shape (idem-001/002) · a new edge with the same (from, type, context) closes the old one; point-in-time queries respect validity (bitemp-001) · every mutation is audited in order (audit-001). Facts: identical fact twice = no-op; conflicts resolved most-recent-wins (by the source time — an older reading arriving late never wins).
- **Failure behaviour:** a write without provenance raises `ProvenanceError` and nothing is stored. The SQLite log is write-through, so a crashed run reopens to exactly the same world. SQLite runs in WAL mode with `synchronous=NORMAL` (B-17: a full sync per event cost ~116 ms on drive E:, 153 events = 18 s → 0.1 s); a VEDA crash loses nothing, a sudden power cut could lose the last few events.
- **Evidence:** `python -m pytest tests/conformance -v --junitxml=logs/conformance.xml` (8/8, Python port of the official cases — the official runner loads TypeScript only) and `python scripts/wm_idempotency_check.py [--mutate]` (port of the official idempotency check).
- **VEDA ingest (`veda_ingest.py`):** `build_network(world, agent, run_id)` loads the curated gauges (`station:jps:<key>`), rivers, districts, gauge links (upstream_of, backup_for, travel_time with lag ranges), places (`place:veda:<id>`) with controlled_by / also_controlled_by / sentinel_for edges, the historic peaks per gauge (one `historic_peaks` fact, highest first, from `veda_pg.historic_peaks`), and the 5 data sources as contexts. `ingest_readings(...)` asserts the current facts (provenance also carries the `sql`; with `check=` the Data & Reconciler agent's health result is stored with each reading, and a reading that fails a check is still written with confidence 0.2): per gauge `water_level_m`, `band`, `change_1h_m`, `change_3h_m` (stamped with the **gauge's reading time**), per place `rain_mm` (stamped with the forecast window end) and `met_forecast_today` (stamped with today's MYT date). All reads go through `run_sql`; re-running both adds **zero events** when nothing changed (live-tested). Mapping edges use `valid_from = 2026-10-22` (mapping v1) — bump it when Dr Ariff's corrections are seeded so old edges close.
- **ContextBuilder (`context.py`):** `ContextBuilder(world).build(intent, place_id)` → structured payload: `gauges` (controlling, secondary), `sentinels` (in curated order, with `travel_time_h` when known), `rain`, `met_forecast`; each item with value, `observed_at`, `age_minutes`, `provenance`, `health`, `tide_influenced` (from the mapping role) and `selection_reason`; `trace.missing` lists anything without data (never invented). Reads only the World Model.

## Data & Reconciler agent (B-13) — `app/agents/data_agent.py`
- **What it does:** gathers the evidence for one plan, only through Zetaris, checks its health and writes it to the World Model. Plain code, no LLM.
- **Prefetch (B-17):** `prefetch(world, now=None)` is the part that needs no plan — refresh an old forecast table, then run the 10 queries (network, readings, `/flood-warning`, data clock) **at the same time** (`veda_ingest.fetch_all`, measured 28 s → 6 s) and load them into the World Model. The loop runs it during planning; `gather(plan, world, pre=...)` uses its results.
- **Inputs:** `gather(plan, world, now=None, pre=None)` (quick plan → no cross-check or reconciliation, trace `data.quick`) — `plan` from the Coordinator (`place`, `intent`, `sources` ⊆ `jps_levels, open_meteo, mygov_forecast, mygov_warning`). `now` defaults to **Zetaris's own clock** (`SELECT current_timestamp()`): live = now, SAMPLE_MODE = when the fixtures were recorded, so ages stay consistent in replay.
- **Steps:** (1) refresh a forecast table (`UNCACHE` + `CACHE TABLE veda_wx.om_rain` / `mygov_forecast`) when the World Model's `refreshed_at` fact for that source is older than its "fresh" limit or missing, and record the new time — this is how forecast age becomes known (skipped and logged in SAMPLE_MODE) · (2) `build_network` + `ingest_readings(check=…)` · (3) `ContextBuilder.build` for the place, then drop items the plan did not ask for · (4) freshness per item · (5) agreement check: data.gov.my `/flood-warning` uses the same station ids as JPS; its newest reading is 23 Feb 2024 → flagged **stale and excluded**, recorded on the World Model context `source:veda:mygov_flood` (`status`, `newest_reading`, `excluded`) · (6) one `health` fact per source per run on `source:veda:<key>`.
- **Health checks (tentative limits, Dr Ariff):** fresh — JPS ≤60 / ≤180 min, Open-Meteo ≤360 / ≤720, MetMalaysia forecast ≤720 / ≤1440 (fresh / aging; older = stale) · schema — level is a number, change/threshold values numeric, rain values present and numeric, forecast text present · plausible — level within −5…120 m, not more than 15 m above danger, change ≤ 3 m in 1 h, rain 24 h ≤ 1000 mm.
- **Reconciliation (B-14):** when two sources give the same quantity (today: a gauge's level from JPS and from data.gov.my `/flood-warning`), `reconcile()` picks the **more reliable** source (reliability on each source's World Model context, tentative: JPS 0.9, flood-warning 0.9, MET forecast 0.8, MET warnings 0.9, Open-Meteo 0.6); on a tie the **newer** reading wins; values within 5 cm simply agree; a source without a value is left out (`single`); if neither rule decides, the quantity goes into **`conflicts_unresolved`** (flagged, never guessed). Every decision is one `reconciliation` entry (`quantity, candidates, chosen, value, rule, reason`) and a `data.reconcile` trace line.
- **Outputs:** `{place, clock, usable, context, sources: {key: {status, note}}, cross_check, reconciliation, conflicts_unresolved, notes, events_added}`. `status` ∈ ok | degraded | stale | failed | skipped. `usable` = the controlling gauge has a reading that is fresh or aging and passed the checks. Every reading fact carries `{sql, query_hash, at, view, agent, run_id, health}`.
- **Failure behaviour:** never raises for data problems. Zetaris down → `usable=False`, every wanted source `failed`, a plain note. A failed refresh → trace `fallback`, the cached copy is used and its age is "unknown"; the failure is stored (`refresh_failed_at`) and not retried for 15 min. **Time caps (audit 23 Oct):** each refresh call ≤ 10 s (`REFRESH_BUDGET_S`), each parallel query ≤ 40 s with all tries (`veda_ingest.FETCH_BUDGET_S`); no refresh at all while the `jps_levels` or `rain_and_forecast` circuit is open; a /flood-warning query that failed in the prefetch is not asked again. Trace actions: `data.refresh`, `world.write`, `world.read`, `data.cross_check`, `data.health`.

## Coordinator (B-12) — `app/agents/coordinator.py`
- **What it does:** the agent that talks to the user — Nemotron 3.5 Lightning on Nightshift lane `fast`. The model proposes, code decides.
- **`plan(question, world=None, llm=None, budget_s=None)`** → `{intent, user_type, effort, sources, question_language, place, place_status, place_message, reason, planned_by}`. Allowed values: intent risk_check | evacuation | cut_off | other · user_type resident | family_far_away | school | unknown · effort quick | full · language en | ms. Anything else is corrected and listed in the trace's `fixes`; `jps_levels` is always added. **The place always comes from the gazetteer** — first the name the model extracted, then the whole question. With `world`, it writes a `run` context with the intent tags only (question radar — never the question text).
- **`draft(question, plan, evidence, forecast=None, card=None, llm=None, feedback=None, previous=None, use_model=True, skip_reason=None)`** → `{text, language, drafted_by (llm | code | fallback), explanation, card, safety_line}`. **B-21:** the answer is the **card** (`app/card.py`) in the user's language; on the full path Nemotron writes **only a short explanation** (2–3 sentences) from the card text and the Forecast agent's reasons, and it is inserted only if `card.explanation_problem` passes (every number must be in the card, compared by value; no other verdict word; ≤ 400 characters). Quick path / no time / Nightshift down / failed check → the card alone (`drafted_by` code or fallback), still in BM or EN. **Revise:** the model gets its previous explanation + the Critic's problems and fix. `low_confidence_answer(...)` = the card alone with a "Low confidence" line, in the user's language. `template_answer(card, lang, why)` = the card alone, used when the AI Critic could not check the explanation (skipped or timed out) - the explanation is dropped and the reason traced.
- **Draft input (Husaini 23 Oct):** `{language, intent, user_type, FACTS: card.key_facts(...), WHY}` - no card text and no user question (who is asking travels as `user_type`); the explanation is ≤ 200 characters. One Nemotron call (4000 tokens), retried **once** only when it failed within 15 s (`DRAFT_FAST_FAIL_S`) and ≥ 45 s of budget are left (trace `draft.retry`); otherwise the card goes out without the explanation.
- **Note (22 Oct night):** the loop no longer calls `plan()` — planning is in code (`router.code_plan`); `plan()` stays as the tested model-planning option.
- **Failure behaviour:** Nightshift error (down, invalid JSON after one repair, SAMPLE_MODE before B-18) → a plan / answer written by code from the same evidence (`planned_by` / `drafted_by` = `fallback`, trace status `fallback`). A model draft that fails the check is replaced the same way, with the reason in the trace. `llm` can be injected (tests use a stand-in; default `nightshift.chat`).

## Agent loop (B-12 skeleton; B-17 completes it) — `app/loop.py`, `run.py`
- **What it is:** a plain Python state machine — `plan → gather → forecast → draft → critique → (revise → critique) → done` — every state change is one trace line (`System | state`).
- **Inputs / outputs:** `loop.run(question, llm=None, world=None, now=None, budget_s=None)` → `{run_id, status, answer, plan, evidence, forecast, reviews, timing, trace}`. CLI: `python run.py "Is Rantau Panjang at risk?"`.
- **Now:** `forecast` runs the Forecast agent (B-16); `critique` runs the Critic (B-14). A rejection goes to `revise` (the Coordinator redrafts with the Critic's problems) and back to `critique`; after **2 rejections** the answer is the code-written summary labelled **low confidence** (`coordinator.low_confidence_answer`). A place that is not found ends after `plan`. World Model: `data/world/world.sqlite` when live (audit in `logs/worldmodel-audit-<run>.jsonl`), in memory in SAMPLE_MODE. **B-17:** while the Coordinator plans, the Data & Reconciler agent's `prefetch` already loads the world in a background thread. **Paths:** quick = river levels + MET forecast, no cross-check or reconciliation, forecast mode `now`, Critic = code checks only; full = everything. **Time budget** from the start of the run: quick 30 s, full 150 s (`BUDGET_S`); the planning call is capped at 30 s; with less than 10 s left (`MIN_MODEL_S`) no model call starts — the answer is written by code and/or the review is code (+ Zetaris) only, each with a `System | budget` trace line saying why. Every `state` line shows the elapsed time and budget left; a `System | timing` line closes the run (per-state seconds, total, within/OVER budget); `run()` also returns `timing`. **Routing (22 Oct night):** the `plan` state starts in code — the gazetteer finds the place (not covered → done, no AI call), the router (`app/router.py`) decides quick or full and the answer language; quick = plan and answer by code, no Nemotron call at all; full = Nemotron plans but cannot change the effort, place or language. `run(..., on_step=fn)` calls `fn(record)` for every trace step as it happens (live progress: `run.py` prints one short line per step; `--verbose` prints every trace sentence; the web page will use the same hook).
- **Failure behaviour:** a 10-minute deadline stops the loop with what is safe to say; any unexpected error writes a `failed` line and still closes the trace. Zetaris unreachable in the plan state (no keys without SAMPLE_MODE, or an outage) → `data.unavailable` trace line and a "VEDA cannot reach its river data right now" answer in the user's language (status `fallback`, no verdict), never a crash (audit 23 Oct).

## Forecast agent (B-16) — `app/agents/forecast_agent.py`
- **What it does:** turns the evidence into a verdict — `NORMAL | WATCH | PREPARE | ACT | INSUFFICIENT_DATA` — with a range and a confidence. Plain code; every verdict lists the rules that fired.
- **Inputs:** `forecast(plan, evidence, world=None)` — the Data & Reconciler evidence (controlling gauge(s), sentinels with travel times, rain) and the plan's `effort` (`quick` → mode `now`: current levels only).
- **Rules (D-06, tentative — Dr Ariff):** ACT = controlling gauge ≥ Danger, or projected to reach Danger within 12 h · PREPARE = ≥ Warning, or Danger within 24 h, or an upstream sentinel ≥ Danger, or rain next 72 h ≥ 200 mm / next 24 h ≥ 150 mm · WATCH = ≥ Alert, or Alert within 24 h, or a sentinel ≥ Alert, or next 72 h ≥ 100 mm on wet ground (past 7 days ≥ 150 mm) · rising fast (≥ 0.3 m/h) → one level up · **fail-safe:** no fresh, healthy controlling reading (or no thresholds) → `INSUFFICIENT_DATA`, never NORMAL (B-41).
- **Trend:** two rise rates (last 1 h; last 3 h ÷ 3) → projection range at +6 / 12 / 24 h and hours-to-threshold `{earliest, latest}`; triggers use the **earliest** time (safety first); nothing projected beyond 24 h (24–48 h = upstream gauges + rain only). **Tide-influenced gauges** (mapping role says so: Tambatan Diraja; Kok Majid tentative) are judged on level only — no projection, no "rising fast".
- **Outputs:** `{verdict, level_name {en, ms} (Normal/Waspada/Amaran/Bahaya; None for INSUFFICIENT_DATA - no band from an unusable reading), mode, triggers [{level, rule, reason}], confidence {score, label, reasons}, controlling [{level, band, rate_m_per_h, projection_m, hours_to, rising_fast, tide_influenced, trend_note}], upstream [{gauge, band, rising, arrives_in_h}], rain, history [top 3 peaks vs now], bigger_than_2014, not_checked, rules}`. Confidence starts at 0.85 and drops for aging data, quick mode, tidal gauge, unknown or disagreeing trend, tentative travel times, unconfirmed rain age, an unusable second controlling gauge (≥ 0.7 high, ≥ 0.5 medium, else low).
- **World Model:** reads the controlling gauge's `historic_peaks`; writes a `forecast` fact about the place (verdict, mode, confidence, triggers). Trace: `forecast.verdict`, `world.read`, `world.write`.
- **Not checked yet (named in every output):** MetMalaysia warnings, official warnings / evacuation orders, the 12–24 h step-down wait (A3).
- **Failure behaviour:** never raises; missing pieces lower the confidence or give `INSUFFICIENT_DATA`.

## Critic (B-14) — `app/agents/critic.py`
- **What it does:** checks the Coordinator's draft before the user sees it — Nemotron 3.5 Super VL on lane `deep` (thinking off: measured 36 s vs 56 s with thinking on, same decision). Timeout: up to 100 s per deep call (fast lane 60 s), never beyond the run's time left minus 10 s for the final answer. May **reject**; the loop allows at most `MAX_REJECTIONS = 2`.
- **Inputs:** `review(question, plan, evidence, forecast, answer, world=None, round_no=1, llm=None, use_model=True, recheck_data=True, skip_reason=None)` — the loop turns the model and/or the re-query off for the quick path or when the time budget is nearly used (reason in the trace).
- **Level 1 — code checks (`code_checks`, cannot be overruled):** the Forecast verdict and no other, every decimal from the evidence (`coordinator.draft_problem`) · **never advice to walk / wade / drive / swim through water**, English and Malay (`critic.unsafe_sentences`: wade, drive/walk through, go through, cross the road, safe to travel, redah, meredah, harung, lalu/melalui air…). It is a warning only when a negation stands right before the phrase (at most 4 words between; "not" / "tidak" directly before) or a danger word follows it ("… is deadly"). "Don't worry" / "jangan risau" is not a negation (audit 23 Oct) · the JPS level name (EN or BM) and the confidence label are stated · the excluded stale source is mentioned · every `conflicts_unresolved` item is mentioned.
- **Level 2 — its own Zetaris re-queries (`requery`, round 1):** the controlling gauge's newest **raw** reading from `veda_pg.river_levels` (not the Data & Reconciler's view; in a replay: `veda_pg.replay_levels`, reported rows only, cut at the replay time); each re-query is capped at 10 s (`RECHECK_CAP_S`) — same time + same level = confirmed, same time + different level = **conflict**, newer raw reading = noted; and the newest date in data.gov.my `/flood-warning` — stale (> 3 h) is **confirmed by the Critic itself** and written to the World Model as `stale_confirmed`; stale but not excluded by the evidence = conflict.
- **Level 3 — AI review (Husaini 23 Oct: the small facts-only call, `_small_review`):** with a card, the model gets only `card.key_facts(card, forecast)` (place, verdict, JPS level, level vs Alert / Danger, trend word, 24 h range, confidence, 2014 difference, excluded sources, conflicts, upstream, MET warnings; ~200 tokens) and the model-written explanation, with one question: does the explanation contradict, exaggerate or downplay any fact? Reply `{ok, reason}`. Lightning (lane `fast`), reasoning off, streaming, `SMALL_MAX_TOKENS` = 2000 (200 gave only empty replies). A failure that comes back within `FAST_FAIL_S` (10 s) is retried up to `MAX_RETRIES` (2) times while the budget allows (trace `critic.retry`); a slow failure (~45 s cut-off) is not. `ok=false` → reject, problem `unsupported: <reason>`, the Coordinator rewrites the explanation once and it is checked again. No AI-written explanation (card by code) → no AI call, nothing for it to judge. The user's question is never sent. Without a card the older full review call (`CRITIC_SYSTEM`) is still used.
- **Outputs:** `{decision: approve | reject, problems (each with by: code | zetaris | model), fix, round, checked_by, recheck}`. Any code or Zetaris problem → reject, even if the model approved (traced). Trace: `critic.code_checks`, `critic.requery`, `critic.review` (status `approved` / `needs_revision`), `world.read` (the stored forecast), `world.write` (a `critic_review` fact about the place).
- **Lane (23 Oct, Husaini):** `VEDA_CRITIC_LANE` = `fast` (default: Nemotron Lightning — the deep lane failed all 12 live attempts on 22–23 Oct, Nightshift's 45 s cut-off / NVIDIA 500s) or `deep` (Super VL first, then the fallback below). The trace and the result say which lane reviewed (`critic_lane`).
- **Fast-lane fallback (23 Oct):** if the deep call fails and at least 20 s are left, the Critic reviews once on the fast lane (Nemotron Lightning) — `critic.fallback` trace line; the result says `critic_lane: fast`.
- **Failure behaviour:** Nightshift unavailable (SAMPLE_MODE before B-18, outage) → review by code + Zetaris only, decision from their findings, noted in the trace. A failed re-query is reported, not fatal. Never raises.

- **Inputs:** `route(question, place, world, pre)` — the question, the gazetteer's place, the World Model and the Data & Reconciler prefetch (readings + MetMalaysia warnings).
- **Full if ANY:** a linked gauge (controlling, second controlling or upstream sentinel) ≥ Alert · a rising trend (≥ 0.3 m in 3 h or ≥ 0.15 m in 1 h; tide-influenced gauges excluded) · an active MetMalaysia rain / thunderstorm warning for the area (`data_agent.met_warnings`: must name Kelantan — or the place's district when districts are listed — and be valid now; sea / wind warnings don't count; a feed whose newest warning is > 24 h old is **stale** and triggers nothing) · a stale or missing source (a linked gauge without a fresh reading; no rain or MET forecast data) · the question mentions evacuation, being cut off, rising water or the coming days (BM, EN and Kelantan-dialect word lists, whole words only). ## Answer card (B-21) — `app/card.py`
- **What it is:** one forwardable answer per place, assembled by CODE, in BM and English (D-07).
- **`build(plan, evidence, forecast)`** → card data: place, verdict, JPS level name, the advice for the verdict (`ADVICE`, tentative — review pack G), the reading (level, time, gauge), comparison with Alert / Danger and the highest recorded peak, the 24 h range, confidence, tide note, rain next 24 h, upstream gauges at Alert or rising (with travel time), active MetMalaysia warnings, sources with age, the excluded stale source, unresolved conflicts.
- **`render(card, lang, explanation=None, low_confidence=False)`** → plain text, user-first order: **what to do now** → **verdict + JPS level** → river vs thresholds and past peak → range + confidence → rain → [Nemotron's explanation, full path only] → upstream → warnings → sources → excluded / conflicts. The disclaimer + 999 / 991 is the answer's `safety_line` in the same language. At most `MAX_CARD_CHARS` = 900 characters (about one phone screen; the BM ACT card is ~760).
- **Verdict words (Husaini 23 Oct, tentative):** the card shows `VERDICT_LABEL` in the answer's language — EN NORMAL / WATCH / PREPARE / ACT / INSUFFICIENT DATA, BM NORMAL / BERJAGA-JAGA / BERSEDIA / BERTINDAK / DATA TIDAK MENCUKUPI (not Waspada / Amaran / Bahaya: those are JPS level names). `verdict_codes(text)` reads either language back to the code, so the Critic's, the coordinator's and the explanation's verdict checks catch a wrong verdict in BM too (capitals only: the verb "bersedia" doesn't count). BM cards use BM month names (`months_ms`: Okt, Dis…). The API's `verdict` field stays the code.
- **Length cap (Husaini 23 Oct): ~750 characters** (`MAX_CARD_CHARS`; the disclaimer and the AI explanation, now ≤ 200 characters, come on top). Over the cap `render` applies `FIT_STEPS` one by one until it fits: shorter gauge name (`Sg. Golok`) → shorter replay source → shorter reading label that keeps its reading time ("bacaan JPS dilaporkan (Kosmo), 27 Nov 19:30") → drop the "vs peak" part when the 2014 line is there → shorter excluded-source line (never dropped: the Critic checks it) → drop the rain line → drop the upstream lines. A line whose rule fired the verdict (`card['keep']`: sentinel → upstream, rain) is never dropped; the action, verdict, river level, 2014 line, range + confidence, MET warnings and sources always stay, so a card that needs all of them can pass 750 (worst case measured: BM ACT with a MET warning, 784). A reconstructed reading always says "estimated:" / "anggaran:". The trace keeps everything.
- **`explanation_problem(text, card)`:** the only gate for model text — empty, too long, a different verdict word, **any number not shown in the card** (by value, both languages), **a flipped comparison** (above/below or di atas/di bawah Alert, Danger or the peak when the card says the other side), or **reassuring words under a WATCH / PREPARE / ACT card** (calm, no need to move, all is fine, masih selamat, tidak perlu pindah…) → rejected (audit 23 Oct).
- **`place_reply(res, lang)`:** "Did you mean…?" / not covered + nearest covered place, in BM or EN.
- **Failure behaviour:** missing pieces are left out, never invented; INSUFFICIENT DATA shows its own advice and "no fresh reading from the controlling gauge" (in a replay: "This replay has no verified JPS reading near this time" + "Last verified reading … too far from this time to use" — the gap is in what was reported, not a gauge that went down; Husaini 23 Oct). The Critic's code checks pass a code-written card by construction (tested in both languages).

## Flood replay data (B-70) — `data/replay/nov2024_anchors.csv`, `scripts/build_replay.py`, `veda_pg.replay_levels`, `veda_wx.om_rain_nov2024`
- **Anchors:** real JPS readings quoted by a cited news report, one row each with the source URL, the quoted sentence and whether its time is exact: Rantau Panjang 8.27 m (26 Nov ~08:00, "this morning") and 8.41 m (26 Nov ~18:00, in a report published 18:21) — Bernama citing publicinfobanjir; Kg Jenob 25.15 m (26 Nov 14:30) — same report; Rantau Panjang 10.94 m (27 Nov 2024 19:30) — Kosmo citing Infobanjir (a reading, not the event peak). Labels, verbatim in the data, trace and card: "reported JPS reading (Bernama…; time approximate)" / "reconstructed between the verified JPS readings 8.41 m (26 Nov ~18:00) and 10.94 m (27 Nov 2024 19:30)". `time_exact` is false when either end is approximate. A replay time inside a long gap (27 Nov 08:00: last reading 14 h old) therefore gives INSUFFICIENT DATA with the last reading for context.
- **Rain:** `setup_wx.py` adds the Zetaris REST table `veda_wx.om_rain_nov2024` = Open-Meteo **archive** (ERA5), hourly rain at the 7 rain points, 15 Nov – 2 Dec 2024 (host `archive-api.open-meteo.com` added to the REST allow-list). - **Failure behaviour:** any anchor problem → nothing is written, the problems are printed and traced; the scenario is replaced in one transaction.

## Flood replay mode (B-70) — `python run.py --replay nov2024 --at "2024-11-26 18:00" "<question>"`
- **What it does:** runs the full agent loop as if it were the replay time, on real Nov 2024 data. Scenes: 26 Nov 18:00 (Rantau Panjang 8.41 m, Warning → PREPARE) and 27 Nov 19:30 (10.94 m, Danger → ACT); verdicts come from the same rules at run time.
- **No hindsight:** the clock is the replay time; `veda_ingest.replay_sqls()` cuts the gauge rows (`observed_at <= …`) and the hourly archive rain (`t <= …`, past 24 h / 7 days) **in the SQL**, so later data never enters VEDA; historic peaks dated at or after the replay time are hidden (`forecast_agent.peak_time`); today's MetMalaysia forecast and warnings are not used ("not available in replay: data.gov.my keeps no 2024 archive"); no forecast refresh. The data.gov.my /flood-warning stale check still runs and is naturally stale.
- **Separate world:** a fresh in-memory World Model per replay run — 2024 facts never mix with today's.
- **Labels:** the answer's first line is always the scenario title "REPLAY · Nov 2024"; the river line is followed by the reading's label (EN in the data, rendered in BM for BM answers); the card adds "Compared with 2014: …" and "Rain past 24 h … (Open-Meteo archive); no rain forecast in a replay". The Critic's code checks require "REPLAY" in a replay answer.
- **Confidence:** a trend built on readings with approximate times is held at **medium** (Husaini 22 Oct night).
- **Budget:** `REPLAY_BUDGET_S` = 240 s, traced on the `System | replay` line ("replay budget 240 s"); live runs stay 150 s.
- **Offline:** both scenes' Zetaris results are recorded as SAMPLE_MODE fixtures (`tests/test_replay.py`).
- **Known limit:** the straight-line 24 h projection on a steeply rising river overshoots (27 Nov: 13.75–14.54 m, while the river peaked ~11.4 m on 28–29 Nov) — the rule itself is review-pack question A5.

## Safety gate (B-58) — `app/safety.py`
- **What it is:** the LAST check on every answer before it leaves VEDA, in code, after the Critic, on every path (quick, full, fallback, replay, place not covered) — BUILD_BRIEF section 7 in one place. `loop.run` calls `safety.gate(answer, card, evidence, forecast)` once at the end.
- **Rules:** (1) NORMAL while the controlling data is not usable → the INSUFFICIENT DATA card · (2) any sentence advising to walk / wade / drive / swim through water (EN + BM, the same `critic.unsafe_sentences` check; only a negation right before the phrase makes it a warning) → the card without the AI explanation · (3) the disclaimer + 999 / 991 in the answer's language · (4) a projected range with no width (e.g. "12.2-12.2 m" from a straight-line reconstruction) → the range line is dropped, never a single precise number · (5) a replay answer starts with its "REPLAY · …" title.
- **Outputs:** the answer with `answer["safety"]` = the list of fixes; one `System | safety` trace line ("all safety checks passed" or each fix).
- **Failure behaviour:** never raises; if the card's own wording were ever unsafe the trace says BUG (tested: every advice line in both languages passes).

## Entry points (B-19) — `app/main.py`, `app/web/index.html`, `app/progress.py`, `run.py`
- **Start:** `python -m app.main` → http://127.0.0.1:8000 (`VEDA_HOST` / `VEDA_PORT`; 127.0.0.1 by default so it is not open to the LAN). CLI: `python run.py "<question>"` (`--verbose`, `--replay nov2024 --at "2024-11-26 18:00"`).
- **`GET /health`:** `{status, sample_mode, zetaris, nightshift}` — Zetaris and Nightshift are pinged (not in SAMPLE_MODE); `degraded` if either does not answer.
- **`POST /run`** `{"question", "replay"?, "at"?}` → `{run_id, trace_id, status, output (answer + disclaimer), language, verdict, confidence, drafted_by, approved_by_critic, safety_fixes, agents, log_file, execution_time, timing, card {en, ms}, disclaimer {en, ms}}`.
- **`GET /run/stream?question=…&replay=…&at=…`:** Server-Sent Events — one `step` event per important trace step as it happens (`progress.describe`, the same short lines as the CLI), then one `result` event (the JSON above) or an `error` event.
- **`GET /`:** the web page — question box, Live / REPLAY · Nov 2024 scenes, the steps appearing live, then the answer in the user's language with an EN / BM switch (the other language shows the code-written card + its disclaimer). No external scripts or fonts (works offline); light and dark (the button text is dark on the light-blue accent in dark mode, [JPS reading]:1). Under the box, a privacy notice in EN + BM: don't type names, IC, phone or address; an AI model (NVIDIA Nemotron via Nightshift) reads the question; it is kept in local log files; phone, IC and email are masked first. Footer: the disclaimer and the data credits with links (JPS Public Infobanjir, data.gov.my, Open-Meteo CC BY 4.0, Bernama / Kosmo for the replay). The answer box carries the answer's `lang`.
- **Privacy (audit 23 Oct):** the question is masked (`trace.redact`: phone, IC, email, secrets) before it goes to either model, and both prompts treat it as quoted data, never as instructions. The uvicorn access log drops the query string (`_NoQueryString`), so `GET /run/stream?question=...` is logged as `GET /run/stream`.
- **Failure behaviour:** bad input → **400** `{"error": {"code", "message"}}` (empty or > 500-character question, unknown replay, bad time, time outside the replay window, `at` without `replay`, not JSON); a second run while one is running → **429** (one writer for the World Model on disk); a model failure never becomes a 500 page (agents fall back; 503 only if one ever escapes); the same for Zetaris (`data_unavailable`). Every returned text is redacted like the trace.

## Self-healing (B-15) — `data_agent.heal`, `data_agent.circuit_open` / `record_call`
- **Ladder, for every gauge an answer needs** (each decision = one `data.heal` trace line): (1) fresh / aging reading → used · (2) silent or stale → a **backup gauge** with a fresh reading: the mapping's `backup_of` pair (today only Kusial ↔ Kusial Baru) and, for a place with a second controlling gauge (Tumpat: Kok Majid → Kuala Jambu), that one — the backup takes the controlling role, labelled; confidence is held at **medium** ("backup gauge in use (X silent)") · (3) no fresh backup → the **last reading is kept for context only** ("Last reading: [JPS reading] m at … – too old to use") and never used for the verdict, so the controlling gauge gives **INSUFFICIENT DATA**. Rantau Panjang, Kota Bharu and Pasir Mas have no controlling-gauge backup yet (a mapping question for Husaini / Dr Ariff).
- **Card:** "Note: Kok Majid has no reading since … – using the backup gauge Kuala Jambu" / "Nota: … menggunakan stesen ganti …"; the last-reading line in BM and EN.
- **Circuit breaker, per source group** (`jps_levels`, `rain_and_forecast`, `mygov_warning`, `mygov_flood`): 3 failures in a row → its queries are **skipped for 15 minutes** (`data.circuit` trace line, "open until …"); then one trial call (half-open) — success closes it, failure opens it again. State = `fail_count` / `open_until` on the source's World Model context, so it survives across runs (live World Model on disk). It runs on real time, never in a replay. An open JPS circuit → INSUFFICIENT DATA at once with an honest note, instead of 30 s timeouts.
- **Rain no longer takes the gauges down:** the rain + MET forecast view (`place_risk_inputs`) is now an optional query — if it fails or its circuit is open, the answer has no rain / forecast line but the gauges and verdict still work.
